Detalhamento de Cada Etapa

1. CREATE (RECEIVED) - Chegada do cliente

Acao do usuario: Atendente registra OS no sistema Dados necessarios: Cliente, Veiculo, Usuario que criou, Pecas iniciais, Servicos iniciais FLUXO ATUAL: 1. Valida se Customer existe → Precisa de CUSTOMER (leitura) 2. Valida se Vehicle existe → Precisa de VEHICLE (leitura) 3. Valida se User existe → Precisa de USER (leitura) 4. Busca Parts (preco, estoque) → Precisa de PARTS (leitura + escrita) 5. Busca Services (preco) → Precisa de SERVICES (leitura) 6. Reserva estoque das pecas → MODIFICA PARTS (escrita) 7. Calcula total 8. Salva OS com status RECEIVED 9. Salva historico DEPENDENCIAS: ├── Customer Service (leitura) - validacao ├── Vehicle Service (leitura) - validacao ├── User Service (leitura) - validacao ├── Parts Service (leitura + ESCRITA) - busca preco + RESERVA ESTOQUE └── Services Service (leitura) - busca preco

2. ASSIGN MECHANIC (IN_DIAGNOSIS) - Atribuir mecanico

Acao do usuario: Gerente atribui mecanico a OS Dados necessarios: ID da OS, ID do mecanico FLUXO ATUAL: 1. Valida se OS existe e esta em RECEIVED 2. Valida se mecanico existe e tem role MECHANIC → Precisa de USER (leitura) 3. Atualiza OS com mecanico 4. Muda status para IN_DIAGNOSIS 5. Salva historico DEPENDENCIAS: └── User Service (leitura) - validacao do mecanico

3. UPDATE ITEMS - Adicionar pecas/servicos durante diagnostico

Acao do usuario: Mecanico adiciona pecas/servicos que identificou Dados necessarios: ID da OS, lista de pecas/servicos FLUXO ATUAL: 1. Valida se OS existe 2. Restaura estoque anterior → MODIFICA PARTS (escrita) 3. Busca novas Parts (preco, estoque) 4. Busca novos Services (preco) 5. Reserva novo estoque → MODIFICA PARTS (escrita) 6. Recalcula total 7. Atualiza OS DEPENDENCIAS: ├── Parts Service (leitura + ESCRITA) - restaura antigo + reserva novo └── Services Service (leitura) - busca preco

4. UPDATE STATUS → AWAITING_APPROVAL

Acao do usuario: Mecanico finaliza diagnostico Dados necessarios: ID da OS, novo status FLUXO ATUAL: 1. Valida se OS existe 2. Valida transicao de status valida 3. Atualiza status 4. Salva historico DEPENDENCIAS: Nenhuma externa (apenas OS)

5. APPROVE (IN_PROGRESS) - Cliente aprova orcamento

Acao do usuario: Cliente aprova execucao do servico Dados necessarios: ID da OS, documentNumber do cliente (do JWT) FLUXO ATUAL: 1. Valida se OS existe e esta em AWAITING_APPROVAL 2. Valida se documentNumber confere com cliente da OS 3. Confirma consumo do estoque reservado → MODIFICA PARTS (escrita) 4. Muda status para IN_PROGRESS 5. Salva approvedAt 6. Salva historico DEPENDENCIAS: └── Parts Service (ESCRITA) - confirma consumo do estoque *** PAGAMENTO DEVERIA ENTRAR AQUI? ***

6. REFUSE (COMPLETED) - Cliente recusa orcamento

Acao do usuario: Cliente recusa o orcamento Dados necessarios: ID da OS, documentNumber do cliente FLUXO ATUAL: 1. Valida se OS existe e esta em AWAITING_APPROVAL 2. Valida se documentNumber confere 3. Restaura estoque reservado → MODIFICA PARTS (escrita) 4. Muda status para COMPLETED 5. Salva finishedAt 6. Salva historico DEPENDENCIAS: └── Parts Service (ESCRITA) - restaura estoque

7. UPDATE STATUS → COMPLETED/DELIVERED

Acao do usuario: Mecanico finaliza / Cliente retira DEPENDENCIAS: Nenhuma externa *** PAGAMENTO DEVERIA ENTRAR AQUI? ***

Decisoes Definidas

  • Pagamento: No DELIVERED (modelo oficina tradicional - cliente paga ao retirar)
  • Estoque: Totalmente assincrono (cria OS, reserva em background, notifica se faltar)
  • Frontend: Decidir depois (comecar com polling simples, evoluir se necessario)
  • Ordem de extracao: OS primeiro → Parts → Payment

Novos Status para Suportar Fluxo Assincrono

public enum WorkOrderStatus { // Status de processamento PENDING_STOCK("Aguardando estoque"), // Apos CREATE, antes de Parts confirmar STOCK_UNAVAILABLE("Estoque indisponivel"), // Parts informou que nao tem // Status existentes RECEIVED("Recebido"), // Parts confirmou estoque IN_DIAGNOSIS("Em diagnostico"), AWAITING_APPROVAL("Aguardando aprovacao"), REFUSED("Recusado"), IN_PROGRESS("Em andamento"), COMPLETED("Finalizado"), // Novos status para pagamento AWAITING_PAYMENT("Aguardando pagamento"), // Apos COMPLETED, antes de pagar PAYMENT_FAILED("Falha no pagamento"), // Pagamento nao processou DELIVERED("Entregue") // Pago e entregue }

Vantagens desta Arquitetura

  1. Desacoplamento total: OS nao precisa esperar Parts ou Payment
  2. Resiliencia: Se Parts cair, mensagens acumulam no SQS e processam depois
  3. Escalabilidade: Cada servico escala independentemente
  4. Rastreabilidade: correlationId permite rastrear fluxo completo
  5. Retry automatico: SQS tenta novamente em caso de falha
  6. Dead Letter Queue: Falhas persistentes vao para DLQ para analise

Problemas e Desafios desta Arquitetura

1. Como o FRONTEND sabe que a OS foi confirmada?

Opcao Implementacao Complexidade
Polling GET /work-orders/{id} a cada X segundos Baixa
WebSocket Conexao persistente para notificacoes Media
Server-Sent Events Stream unidirecional do server Media
Push notification Para mobile Alta

2. E se a mensagem for processada duas vezes?

Solucao: Idempotencia

  • Cada mensagem tem um idempotencyKey
  • Antes de processar, verifica se ja processou
  • Se ja processou, ignora

3. E se Parts demorar muito para responder?

Solucao: Timeout + Compensacao

  • OS tem um job que verifica OS em PENDING_STOCK ha mais de X minutos
  • Notifica administrador ou muda para status de erro

Resumo Executivo

O que temos hoje (Monolito)

  • Spring Boot 3.5.5 com Clean Architecture
  • PostgreSQL 16 com Liquibase
  • 11 endpoints de OS
  • Estoque manipulado diretamente (sincrono)
  • Sem fluxo de pagamento

O que teremos (3 Microservicos)

  • OS Service: Gerencia ordens de servico
  • Parts Service: Gerencia estoque e pecas
  • Payment Service: Processa pagamentos (a ser criado)
  • Comunicacao via Amazon SQS (assincrono)
  • Cada servico com seu proprio banco

Principais mudancas no fluxo

  1. CREATE retorna 201 imediato, estoque reserva em background
  2. APPROVE/REFUSE atualizam status imediato, estoque ajusta em background
  3. DELIVERED so acontece apos Payment Service confirmar pagamento
  4. Novos status: PENDING_STOCK, STOCK_UNAVAILABLE, AWAITING_PAYMENT

Filas SQS necessarias

  • 4 filas OS → Parts (reservation, adjustment, consumption, restoration)
  • 1 fila Parts → OS (response)
  • 1 fila OS → Payment (ready-for-payment)
  • 1 fila Payment → OS (payment-completed)
  • 2 DLQs (stock-dlq, payment-dlq)
  • Total: 10 filas

Riscos identificados

  1. Consistencia eventual (cliente ve status intermediario)
  2. Mensagens duplicadas (precisa idempotencia)
  3. Timeout de operacoes (precisa compensacao)
  4. Complexidade de debug (rastreamento distribuido)

Proximos passos imediatos

  1. Desenhar contratos das mensagens SQS (JSON schema)
  2. Criar POC de comunicacao via SQS no monolito
  3. Definir estrategia de polling para frontend
  4. Planejar migracao de banco de dados

Como o cliente sabera que a operacao async terminou?

3. O Maior Problema: Gestao de Estoque

O codigo em WorkOrder.java (linhas 193-232) manipula diretamente o estoque de pecas:

// Ao CRIAR OS (linha 198) part.getPart().getStock().subtract(part.getQuantity()); // Ao APROVAR OS (linha 220) stock.subtractReservedStock(totalQuantity); // Ao RECUSAR OS (linha 230) part.getPart().getStock().restore(part.getQuantity());

E em CreateWorkOrderUseCaseImpl.java (linhas 85-86):

workOrder.reserveParts(); partGateway.saveAll(parts); // Salva estoque modificado

Por que isso e um problema?

  1. Transacao Distribuida: Hoje tudo roda em uma unica transacao ACID. Ao separar, precisamos de saga ou 2PC.
  2. Consistencia: Se o servico de OS cair apos reservar estoque, o estoque fica inconsistente.
  3. Rollback Complexo: Compensacao manual e necessaria em caso de falha.

4. Problemas e Desafios para Discussao

Problema 1: Consistencia Eventual (CRITICO)

Com processamento assincrono, o cliente recebe 202 Accepted mas a operacao ainda nao terminou.

Cenarios problematicos:

  1. Cliente cria OS → recebe ID → tenta GET imediatamente → OS ainda esta PENDING_STOCK
  2. Cliente aprova OS → recebe 202 → tenta ver status → ainda esta APPROVING
  3. Duas requisicoes de approve chegam antes da primeira terminar → duplicacao?

Solucoes:

  • Idempotencia: Usar idempotency key no header para evitar duplicacao
  • Documentacao clara: Cliente deve entender que 202 ≠ operacao completa
  • Timeout/retry: Implementar Dead Letter Queue + alerta para operacoes travadas

Problema 2: Tratamento de Falhas

E se o Part Service nao responder?

Cenario: OS publica "StockReservationRequested" mas Part Service esta fora

Solucao com SQS:

1. Mensagem fica na fila (SQS retem por ate 14 dias) 2. Part Service volta → processa mensagens pendentes 3. Se passar de X minutos → move para DLQ 4. Worker de compensacao processa DLQ: - Atualiza OS para STOCK_FAILED - Notifica administrador

Problema 3: Ordenacao de Mensagens

E se mensagens chegarem fora de ordem?

Cenario: 1. Cliente cria OS (StockReservationRequested) 2. Cliente cancela OS antes do estoque ser reservado 3. Part Service processa reserva DEPOIS do cancelamento

Solucoes:

  • SQS FIFO: Garante ordenacao por MessageGroupId (usar workOrderId)
  • Versionamento: Cada mensagem tem version number, ignorar versoes antigas
  • Timestamp: Ignorar mensagens mais antigas que ultimo processamento

Problema 4: Autorizacao do Cliente

Ao aprovar/recusar OS, o sistema valida customer.documentNumber:

if (!Objects.equals(workOrder.getCustomer().getDocumentNumber().getValue(), documentNumber)) { throw new ForbiddenException(...); }

Solucao recomendada: Desnormalizar documentNumber na tabela work_orders

  • Captura no momento da criacao
  • Evita chamada HTTP no fluxo de aprovacao
  • Dado nao muda frequentemente

Problema 5: Foreign Keys no Banco

Atualmente existem FKs para customers, vehicles, users, parts, services.

Opcoes:

  • Remover FKs e validar na aplicacao
  • Manter banco compartilhado inicialmente (schema separado)
  • Desnormalizar dados essenciais (snapshot de precos, nomes)

Problema 6: Estrategia de Migracao

Estrategia Descricao Risco
Big Bang Migrar tudo de uma vez ALTO
Strangler Fig Migrar gradualmente, endpoint por endpoint MEDIO
Branch by Abstraction Criar abstracao, depois migrar BAIXO

Recomendacao: Strangler Fig, migrando endpoints na ordem:

  1. Endpoints GET (sem estoque) - validar infraestrutura
  2. assign-mechanic e status - testar async interno
  3. create - testar saga de estoque
  4. approve/refuse - completar saga
  5. update-items - mais complexo, por ultimo

Problema 7: Comunicacao com Part Service no Monolito

O Part Service permanece no monolito. Como ele vai consumir/produzir mensagens SQS?

Opcao Descricao Esforco
A. Adicionar SQS ao monolito Monolito vira producer/consumer de SQS MEDIO
B. Sidecar/Adapter Container separado que faz bridge HTTP ↔ SQS ALTO
C. API Gateway + Lambda Lambda consome SQS e chama API REST do monolito MEDIO

Recomendacao: Opcao A - adicionar dependencia SQS ao monolito e o caminho mais simples
